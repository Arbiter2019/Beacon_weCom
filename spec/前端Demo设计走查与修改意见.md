# 前端 Demo 设计走查与修改意见

## 1. 走查范围

本次走查基于以下文件：

- 需求文档：`spec/企业微信聊天同步服务.md`
- 前端 Demo：`demo/Web-Prototype/message-archive-prototype.html`
- 设计交付说明：`demo/Web-Prototype/DESIGN-HANDOFF.md`
- 设计清单：`demo/Web-Prototype/DESIGN-MANIFEST.json`

评估重点：

- Demo 是否覆盖需求中的前端信息架构和核心交互。
- 从易用性、布局、可扩展性角度识别设计风险。
- 输出后续可落地的设计修改方向。

## 2. 总体结论

当前 Demo 已基本覆盖需求文档中的核心前端结构：

- 观测员工范围
- 会话列表
- 聊天内容查看
- 学员 / 学员群详情面板
- 图片预览
- 当前会话内消息搜索
- 观测员工配置

整体方向是成立的，适合作为“企业微信会话存档查看工作台”的基础原型。但从正式产品设计角度看，目前仍存在以下主要问题：

1. 高频查看任务和低频配置任务权重接近，主流程不够聚焦。
2. 会话列表的信息语义不够明确，尤其是“最近查看排序”和“最近消息时间”的区别。
3. 搜索能力需要拆分“会话搜索”和“当前对话消息搜索”。
4. 详情面板混入了开发解释型信息，业务用户视角下信息层级可优化。
5. 撤回消息、空状态、无权限、不支持消息类型等审计场景状态需要规范化。
6. 后续消息类型扩展需要更明确的组件边界。

## 4. 主要优化建议

### 4.1 聚焦主流程，弱化低频配置入口

当前“消息查看”和“观测配置”在左侧菜单中权重接近。但实际使用中：

- 消息查看是高频任务。
- 观测范围配置是低频管理任务。

建议：

- 将日常主流程明确为：选择观测员工 → 选择学员 / 学员群 → 查看消息 → 查看详情。
- 保留“观测配置”，但视觉权重低于消息查看。
- 在配置页明确说明：观测范围只影响前端查看权限，不影响底层全量同步。

### 4.2 强化会话列表的信息语义

需求中会话排序规则是：

1. 优先按 `conversation_view_history.last_viewed_at` 排序。
2. 没有查看记录时按最近消息时间排序。

当前 Demo 虽然有“最近查看排序”的提示，但列表项中的时间字段容易被误解。

建议：

- 列表项中明确区分“最近查看”和“最近消息”。
- 对按最近查看置顶的会话增加轻量标签，例如“最近查看”。
- 对群聊会话增加成员数、当前观测员工角色、群主信息。
- 对单聊会话增加“备注名 + 微信昵称”的双层展示，强化备注优先规则。

### 4.3 拆分搜索层级

当前 Demo 同时存在员工搜索、会话搜索和消息搜索，但用户对搜索范围的感知不够稳定。

建议将搜索拆成两类：

1. 会话级搜索
   - 搜索员工、学员、学员群。
   - 用于切换当前观测对象或打开目标会话。

2. 当前对话消息搜索
   - 只搜索当前已打开会话。
   - 支持文本、发送人、时间范围。
   - 抽屉标题和说明中明确“仅搜索当前会话”。

### 4.4 优化详情面板的信息层级

当前详情面板中的“数据映射”对开发和评审有价值，但对业务用户干扰较强。

建议：

- 业务默认态隐藏“数据映射”。
- 如需保留，可放入“调试信息”折叠区或仅在开发模式展示。
- 学员详情优先展示：展示名、微信昵称、备注、描述、标签、关联员工、添加时间。
- 群详情优先展示：群主、管理员、成员数、群状态、群公告、成员列表。

### 4.5 规范撤回消息展示

当前撤回消息使用红色 badge。红色容易被理解为错误或告警，而撤回在审计产品中更接近“事实状态”。

建议：

- 撤回状态使用中性灰或弱警示色。
- 文案建议使用“已撤回”或“该消息已被撤回”。
- 如果产品允许展示原内容，应明确展示策略。
- 如果产品不展示原内容，应在原消息位置保留状态占位，避免时间线断裂。

### 4.6 补齐关键状态设计

当前 Demo 已有部分空状态，但正式设计需要覆盖更多业务状态。

建议补齐以下状态：

- 未选择观测员工。
- 当前没有任何启用观测员工。
- 已选择观测员工但无学员 / 学员群。
- 会话消息为空。
- 消息加载中。
- 消息加载失败。
- 当前用户无权查看该员工或会话。
- 暂不支持的消息类型。
- 图片资源加载失败或 OSS 地址失效。

### 4.7 为消息类型扩展预留组件规范

当前版本支持文本、图片、链接、撤回、同意会话存档等有限类型。需求文档中列出了大量暂不支持类型，后续有较大扩展概率。

建议：

- 按 `msg_type` 抽象消息组件。
- 为暂不支持类型提供统一占位卡片。
- 搜索结果中也使用统一消息摘要规则。
- 图片、文件、链接、小程序、会话记录等未来类型复用统一卡片结构。
- 不支持类型不应直接消失，否则审计时间线会出现缺口。

## 5. 布局优化建议

### 5.1 桌面端

当前四栏布局适合审计工作台，但栏位较多，信息密度偏高。

建议：

- 左侧主导航保持窄栏。
- 观测员工栏和会话列表栏保持稳定宽度。
- 聊天区作为主工作区，应获得最大视觉权重。
- 详情面板继续使用右侧抽屉，避免常驻挤压聊天区。

### 5.2 移动端

当前移动端通过“员工 / 会话 / 聊天”切换承载完整流程，结构可用，但不适合复杂配置。

建议：

- 移动端定位为轻量查看。
- 移动端优先保证员工选择、会话选择、消息查看、详情查看。
- 观测配置在移动端可保留，但不作为核心验收重点。

## 6. 可扩展性建议

建议后续设计和前端实现时，将页面拆成以下稳定模块：

| 模块 | 职责 |
| --- | --- |
| 观测员工选择器 | 搜索和切换启用状态的观测员工 |
| 观测范围配置 | 管理可观测员工范围 |
| 会话列表 | 展示学员和学员群，并承载排序与筛选 |
| 聊天时间线 | 渲染不同类型消息 |
| 消息搜索抽屉 | 搜索当前会话内消息 |
| 信息详情抽屉 | 展示学员、群、成员详情 |
| 图片预览 | 展示图片消息原图或 OSS 资源 |

其中，聊天时间线应优先组件化，避免后续新增消息类型时反复修改主页面结构。

## 7. 建议进入下一轮设计修改的事项

建议下一轮设计修改优先处理以下事项：

1. 调整信息架构权重：突出消息查看主流程，弱化观测配置。
2. 优化会话列表项：补充排序依据、群角色、群成员数、备注名 / 微信昵称。
3. 明确搜索边界：区分会话搜索和当前对话消息搜索。
4. 重构详情面板层级：业务信息优先，开发映射信息降级。
5. 统一审计状态样式：撤回、无权限、空状态、失败态、不支持类型。
6. 制定消息类型组件规范，为文件、小程序、会话记录等未来类型预留扩展。

## 8. 当前不建议优先投入的事项

以下事项当前不建议作为第一优先级：

- 大幅改变视觉风格。当前灰底、高密度、企业微信绿色强调色方向基本成立。
- 过早设计复杂数据分析看板。当前需求核心是会话查看，不是经营分析。
- 在移动端完整承载观测范围配置。该功能更适合桌面工作台。
- 引入过多动效。审计类产品应优先保证稳定、清晰和可扫描。
